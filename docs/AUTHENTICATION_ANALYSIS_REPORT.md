## 1. セキュリティ要件分析

### 1.1 個人情報保護法への対応

#### 方式A: 静的APIキー認証

| 項目 | 評価 | 詳細 |
|------|------|------|
| 個人情報へのアクセス制御 | ⭐⭐ | 単一キーで全データアクセス可能、粒度が粗い |
| 漏洩時の影響範囲 | ⭐ | **全プロジェクト・全ユーザーに影響** |
| アクセスログの記録 | ⭐ | キーが共通のため「誰が」アクセスしたか特定困難 |
| トレーサビリティ | ⭐ | APIキー単位でしかログが残らない |
| **総合評価** | **⭐⭐ (2/5)** | **個人情報保護法の要件を満たさない** |

**リスク**:
- APKを逆コンパイルされると全システムへのアクセス権を取得される
- 漏洩時に全ユーザーの個人情報（氏名、CCUS ID、顔画像、入退場記録）が危険にさらされる
- GDPR相当の「データ主体の権利」（削除権、訂正権）を技術的に保証できない

#### 方式B: OAuth 2.0 Bearer認証

| 項目 | 評価 | 詳細 |
|------|------|------|
| 個人情報へのアクセス制御 | ⭐⭐⭐⭐⭐ | ユーザー単位・プロジェクト単位で権限管理 |
| 漏洩時の影響範囲 | ⭐⭐⭐⭐⭐ | **該当ユーザーのみ、即座に無効化可能** |
| アクセスログの記録 | ⭐⭐⭐⭐⭐ | トークンのsubjectから「誰が」を特定可能 |
| トレーサビリティ | ⭐⭐⭐⭐⭐ | 完全な監査証跡（ユーザーID、タイムスタンプ、操作内容） |
| **総合評価** | **⭐⭐⭐⭐⭐ (5/5)** | **個人情報保護法の要件を完全充足** |

**メリット**:
- トークン漏洩時は該当ユーザーのみ影響、5分で自動失効
- Keycloakの監査ログで全操作を記録（コンプライアンス対応）
- プロジェクト単位でアクセス制御（現場Aのデータを現場Bで見れない）

- **リスクスコア**: **9.0 (Critical)**

**脅威2: 中間者攻撃（MITM）**

- **発生確率**: 中（公衆Wi-Fi使用時）
- **影響**: 高（APIキーが盗聴される）
- **対策**: HTTPS通信（実装済み）
- **リスクスコア**: **4.5 (Medium)**

**脅威3: キー漏洩時の影響範囲**

- **発生確率**: 中（従業員の離職、デバイス紛失等）
- **影響**: 致命的（全システムへのアクセス権を失う）
- **対策**: キー再発行（全アプリ再配布が必要）
- **リスクスコア**: **8.0 (High)**

**総合リスクスコア**: **7.2 / 10.0** ⚠️

**脅威1: トークン盗難**

- **発生確率**: 低（SecureStoreで暗号化保存）

- **リスクスコア**: **2.5 (Low)**

- **リスクスコア**: **1.5 (Low)**

**脅威3: セッションハイジャック**

- **発生確率**: 低（デバイスバインディング可能）

## 2. スケーラビリティ要件分析

### 2.1 マルチプロジェクト対応

#### 方式A: 静的APIキー認証

**課題**:
- プロジェクト単位のアクセス制御が不可能
- データ分離を実現するには、プロジェクトごとに別のAPIキーが必要
- APIキーの管理が複雑化（10プロジェクト → 10個のAPIキー）

**スケーラビリティ**: ⭐⭐ (2/5)

#### 方式B: OAuth 2.0 Bearer認証

**利点**:
- Keycloakのロール設定で柔軟な権限管理
- トークンのクレームに `resource_access: { "mc-gate": { "roles": ["project:PRJ001", "project:PRJ002"] } }` を含めることで、ユーザーがアクセス可能なプロジェクトを動的に制御
- プロジェクト追加時の再ビルド不要

**実装例**:
```typescript
// サーバー側ミドルウェア
function checkProjectAccess(req, res, next) {
  const projectId = req.params.projectId;
  const userRoles = req.user?.resource_access?.['mc-gate']?.roles || [];

  if (!userRoles.includes(`project:${projectId}`)) {
    return res.status(403).json({ error: 'Forbidden' });
  }

  next();
}
```

**スケーラビリティ**: ⭐⭐⭐⭐⭐ (5/5)

---

### 2.2 マルチテナント対応

**シナリオ**: 複数の建設会社（元請）が同一システムを利用

#### 方式A: 静的APIキー認証

**課題**:
- テナント間のデータ分離が困難
- 会社ごとに別のAPIキーを発行する必要があり、管理が煩雑
- カスタマイズ設定（チェック項目の有効/無効等）がテナント単位で不可能

**テナント分離**: ❌ 不可能

#### 方式B: OAuth 2.0 Bearer認証

**利点**:
- Keycloakの組織（Organization）機能でテナント分離
- 各テナントに専用のRealmを作成することで完全分離
- テナントごとのカスタマイズ設定をトークンクレームに含めることが可能

**アーキテクチャ例**:
```
Keycloak
├── Realm: tenant-A (A社専用)
│   ├── Client: mc-gate-mobile
│   └── Users: A社従業員
├── Realm: tenant-B (B社専用)
│   ├── Client: mc-gate-mobile
│   └── Users: B社従業員
```

**テナント分離**: ✅ 完全分離可能

### 2.3 ユーザー数の拡張性

#### 方式A: 静的APIキー認証

**問題点**:
- ユーザー数が増加しても認証処理が軽量（サーバー側検証不要）
- しかし、**同時アクセス数の制御が不可能**
- API Rate Limiting をユーザー単位で実施できない（APIキー単位でしか制限不可）

**Rate Limiting**: ❌ ユーザー単位では不可能

#### 方式B: OAuth 2.0 Bearer認証

**利点**:
- トークンの `sub`（ユーザーID）でユーザーを識別可能
- ユーザー単位でAPI Rate Limiting を実施可能
- トークンキャッシュ（Redis等）で検証処理を高速化（10,000 req/sec 以上）

**実装例**:
```typescript
import rateLimit from 'express-rate-limit';

const limiter = rateLimit({
  windowMs: 60 * 1000, // 1分
  max: 100, // 100 requests per minute per user
  keyGenerator: (req) => req.user.sub, // ユーザーID単位
});

app.use('/api/', limiter);
```

**Rate Limiting**: ✅ ユーザー単位で可能

## 3. 運用性・保守性分析

### 3.1 APIキー/トークンのローテーション

#### 方式A: 静的APIキー認証

**課題**:
- APIキー変更時、全ユーザーのアプリを再配布する必要がある
- EAS Updateでは不可能（APIキーは `app.config.ts` に記載のため、新しいビルドが必要）
- ダウンタイムが発生（古いAPIキーを無効化すると、未更新のアプリが使用不可に）

**影響範囲**: 全ユーザー
**変更時間**: 1〜2週間（ビルド → 配布 → ユーザーインストール）
**リスク**: 高

#### 方式B: OAuth 2.0 Bearer認証

**利点**:
- アクセストークンは5分で自動失効、リフレッシュトークンは30分でローテーション
- ユーザーは何もせずに自動的に新しいトークンを取得
- Keycloak側の設定変更のみで完結（アプリ再配布不要）

**影響範囲**: なし
**変更時間**: 即時
**リスク**: なし

---

### 3.2 ユーザー管理

#### 方式A: 静的APIキー認証

**課題**:
- ユーザーの追加・削除が不可能（APIキーは共通）
- 権限変更（管理者 → 一般ユーザー）が不可能
- 緊急時のアクセス無効化が不可能（APIキーを変更すると全員に影響）

**ユーザー管理**: ❌ 不可能

#### 方式B: OAuth 2.0 Bearer認証

**利点**:
- Keycloak管理コンソールでユーザーを即座に追加・削除
- ロール変更も即座に反映（次回トークンリフレッシュ時）
- 緊急時のアクセス無効化が即座に可能（Keycloakでユーザー無効化 → トークンが即座に無効）

**実装例**:
```bash
# Keycloak Admin CLI
kcadm.sh update users/<user-id> -s enabled=false
# → 該当ユーザーのトークンが即座に無効化される
```

**ユーザー管理**: ✅ 完全対応

---

### 3.3 監査ログ

#### 方式A: 静的APIキー認証

**ログ内容**:
```json
{
  "timestamp": "2025-11-18T12:34:56Z",
  "method": "POST",
  "path": "/api/events",
  "apiKey": "development-api-key-12345",
  "status": 200
}
```

**問題点**:
- 「誰が」アクセスしたかが不明（APIキーが共通）
- 「どのプロジェクトのデータ」にアクセスしたかの記録が不完全
- コンプライアンス監査時に証明が困難

**監査証跡**: ❌ 不十分

#### 方式B: OAuth 2.0 Bearer認証

**ログ内容**:
```json
{
  "timestamp": "2025-11-18T12:34:56Z",
  "method": "POST",
  "path": "/api/events",
  "userId": "user-123",
  "userName": "山田太郎",
  "projectId": "PRJ001",
  "action": "event_create",
  "status": 200,
  "ipAddress": "192.168.1.100",
  "userAgent": "mc-gate-mobile/1.0.11"
}
```

**利点**:
- 完全な監査証跡（誰が・いつ・何を・どうした）
- Keycloakの監査ログと組み合わせることで、ログイン履歴も記録可能
- コンプライアンス監査時に証拠として提出可能

**監査証跡**: ✅ 完全対応

### 3.4 障害対応

#### 方式A: 静的APIキー認証

**障害シナリオ**: サーバー側でAPIキー検証ロジックに不具合

**影響範囲**: 全ユーザー
**復旧手順**: サーバー修正 → デプロイ → 再起動
**復旧時間**: 30分〜1時間
**フォールバック戦略**: なし（モバイルアプリ側でAPIキーをハードコーディングしているため、サーバー側を修正するしかない）

#### 方式B: OAuth 2.0 Bearer認証

**障害シナリオ1**: Keycloakサーバーダウン

**影響範囲**: 新規ログインのみ（既存トークン保有ユーザーは継続利用可能）
**復旧手順**: Keycloakサーバー再起動
**復旧時間**: 5〜10分
**フォールバック戦略**: トークンキャッシュ（最大5分間はオフラインでも検証可能）

**障害シナリオ2**: トークンリフレッシュ失敗

**影響範囲**: 該当ユーザーのみ
**復旧手順**: ユーザーが再ログイン
**復旧時間**: 即時
**フォールバック戦略**: オフラインキュー（ネットワーク復旧後に自動送信）
